第1章　プロンプトエンジニアリングとは
【第1章　プロンプトエンジニアリングとは　要点まとめ】

■この章で持ち帰ること
AIは、正しいことを言う機械ではなく、続きそうなことを言う機械。だから、頼み方で答えが変わる。

■本日の前提
・AIの答えは、プロンプト（聞き方）と、中のモデル（頭脳）の両方で決まる
・サービス（ChatGPT、Copilot、Gemini、Claudeなど）とモデルは別物。同じサービスでも中のモデルは入れ替わる
・モデルの違いは優劣ではなく違い。順位は数か月で入れ替わる
・講師の画面と結果が違っても、それが普通

■AIチャットの仕組み
・手前の文章に、「確率的にありそう」な言葉をどんどんつなげていく（10万年分の読書をした予測変換）
・AIは「正しいから」ではなく「ありそうだから」その言葉を選ぶ。正しさの判定はしていない
・同じプロンプトでも結果が違う理由は2つ
　1. 同じAIでも、ありそうな候補の中から毎回選び直している
　2. 使っているAI（モデル）がそもそも違う（無料版と有料版で違うこともある）

■プロンプトの改善＝書き方を変える
・絞る … 枠を渡す（選択肢、形式）→ 答えのばらつきが小さくなる（演習②）
・寄せる … 欲しい種類を書く（タイ風、材料と手順）→ 答えの中身が動く（カレー）
・渡していない枠は、AIが勝手に埋める。それが「思ったものと違う」の正体
・確率をゼロにはできない。でも偏らせることはできる

■LLMの理解（覚えなくてOK。理由だけ持ち帰る）
・機械学習は、ルールを人が書くのではなく、データから自分で見つける
・記憶は「つなぎ目の強さ」にあり、そのつまみが何兆個もある。中身を人間が読み解くのは難しい
・1語ずつ選んでは足していく。途中で1語違うと、その先が全部変わる
・学習はある時点で止まっている（検索機能で補う場合も、それは覚えている知識ではない）
・学習データは人が全部は確認できない。偏りや誤りも一緒に学んでいる
・後から「振る舞い」を教え込む工程があり、各社の個性になる。それでも「絶対」にはならない
・だから、ファクトチェックが要る
第2章　プロンプトの基本要素
【第2章　プロンプトの基本要素　要点まとめ】

■この章で持ち帰ること
プロンプトは、命令・条件・出力形式を段落に分けて書く。そうすれば、誰がいつ実行しても、同じ体裁の答えが返る。

■プロンプトの4つの部品（料理のレシピで言うと）
命令　　　　何をしてほしいか　　→「料理のレシピを考えて」
文脈　　　　なぜ・どんな背景で　→「明日は子どもの誕生日。腕を振るいたい」
入力データ　渡す資料・材料　　　→「予算5千円。冷蔵庫に卵、生クリーム、牛肉」
出力指示子　仕上がりの形　　　　→「買い出しリスト、かかる時間、作り方を箇条書きで」
・一番効くのは出力指示子。命令とセットで書く。全部入れる必要はない

■3つの原則
・簡潔：関係ないことはノイズになる
・明確：二通りに読める書き方をしない
・具体：「来月」ではなく「10月15日から3日間」。書くほど方向が定まる
・決めたところはそろい、決めなかったところはAIが埋める

■プロンプトを設計する順番
① 命令　　　　　　　これがしたい、を端的に。一番先頭に書く
② 出力形式　　　　　返ってくる形が、実行前から想像できる状態にする（一番効く）
③ 制約条件／禁止事項　言葉で説明できるルール（小学生でもわかる表現で／400字以内／〜しない）
④ 回答例　　　　　　言葉で説明できない「自分らしさ」「弊社らしさ」は、例で渡す（第3章）
※「文章の目的」は言い回しが変わる程度で、出力形式ほどは効かない

■今日から使えるテンプレート
# 命令書
（何をしてほしいか）
# 条件、設定
（空欄なら「まだ決めていない」というサイン）
# 出力形式
（箇条書き、表、見出し名など）
見出しは自由に増やせる（# 必須で含めること、# 制約条件、# 禁止事項 など）
・# は見出しの書き方（マークダウン）。AIが読んだ文章に多い書き方なので、はっきり伝わる

■追加質問（壁打ち）
・これまでのやりとりも、全部プロンプトの一部として渡っている
・アイデア出しや、自分の理解を深めるのに有効。ただし、人に渡せる形にはならない
・何度やり直させても大丈夫。「批判的に見て、改善案を5つ」と頼むと厳しく見てくれる

■ビジネス活用のポイント
・まず使ってみる。完璧を求めすぎない（8割を速く作って、残りを自分で直す）
・個人情報・機密情報は入れない。固有名詞は「〇〇株式会社」「〇〇様」に置き換える
・役割を与えると、自分にない観点を持ってきてくれる（ロールプレイにも使える）
・命令と材料は段落を分ける（### や """ で区切る）
・自分の文体は言葉で説明しにくい → 過去のメールを「# 過去のメール例」として貼る
・［ ］や／で型を渡すと、型どおりに返る
・アイデア出しはあえて絞らない。後工程まで考え、どれを選ぶかは自分の経験で決める
・レビュー：誤字や表記ゆれ、失礼な表現など、自分では気づけない観点が得られる
・分類（LLM-as-a-Judge）：判断基準と例を渡し、正解が分かるデータで必ずテストしてから使う
・Excel・プログラミング：手順で教えてくれる。ただしチェックと判断は人間の仕事
・情報源を出させても、ファクトチェックが済んだことにはならない。中身は自分で当たる

■再現性の確かめ方
・新しいチャットで2〜3回実行して、同じようなものが出るか見る
・決まっている情報は固定し、決まっていない情報は使うときに入力する欄にする
第3章　プロンプトのテクニック
【第3章　プロンプトのテクニック　要点まとめ】

■この章で持ち帰ること
答えを見てから直すのではなく、答えが出る前に、入力側で仕込む。
技法の名前は覚えなくてOK。動きは4つ：例を渡す／考え方を渡す／知識を渡す／先に設定しておく
・Few-Shot は「再現性」を上げる。In-Context は「正確性」を上げる
・CoT・ToT はもともと正確性のための技法。いまは推論モデルが中で自動でやるので、主に「考えの道筋・検討の過程を残す」「視点を広げる」ために使う

■例を渡す（Zero-Shot → Few-Shot）
・ショット＝回答例。例を渡さずに聞くのが Zero-Shot（普段のやり方）
・例をいくつか渡すのが Few-Shot。答えが自分たちの言い方に寄り、何度やってもそろう
・自分たちが用意した例がもとなので、納得して使える（お客様に出せる）
・良かったメール・議事録・企画書は、残しておけば財産になる
・分類に使う手順：例を作る → 正解が分かるデータでテストする → それから本番に使う

■考え方を渡す（CoT・ToT）　※正確さの部分は、いまは推論モデルが中で自動でやる
・CoT（Chain-of-Thought）：答えまでの道筋を渡す。「ステップバイステップで考えて」の一文でも切り替わる
・いまは推論モデルが自動で段階的に考えることも多い。それでも明示して仕込める
・今も書く意味：考える観点をこちらが指定できる／根拠が文字で残る（「AIがそう言ったので」とは言えない）
・「ステップバイステップで」の一文は、速さ重視のモデルを使うときや、途中の計算を確かめたいときに
・ToT（Tree-of-Thought）：複数案を出させ、比べさせ、選ばせ、磨かせる。検討内容は全部残させる
・いまのToTの使いどころ：反対の立場まで出させて視点を広げる／結論に至った過程を文字で残す（正しさが上がるのではなく、検討の幅が広がる）
・向かない場面：事実の照会、単純作業
・途中経過を断られることがある。断られたら同じことを繰り返さない
・プロンプト自体をAIに考えさせることもできる。ただし責任は人間に残る

■知識を渡す（In-Contextラーニング）
・AIが間違える根本原因は知識不足。知らないなら、プロンプトの中に知識を入れて渡す
・知識を渡すと「すんでいません」（断定）が「確認されていません」に変わる
・質問する人と、知識を渡す人が別なら、それはチャットボット

■先に設定しておく（システムプロンプト）
・利用者が質問する前に渡しておく事前設定。役割・制約条件・禁止事項・回答例・知識を全部入れる箱
・アプリに組み込むときは、利用者は裏にAIがいることを知らない。だから事前設定が要る
・保存しておく機能：Copilot＝エージェント／ChatGPT＝GPT（有料）／Gemini＝Gem／Claude＝プロジェクト
・入力するのは3つ：名前／説明文／指示（＝システムプロンプト）
・チャットボットでは、断り方まで例で渡すのがコツ（演習4）
第4章　リスクと誤用
【第4章　リスクと誤用　要点まとめ】

■この章で持ち帰ること
使いこなせるほど、守る話が必要になる。リスクはAIの性能ではなく、使い方の問題。

■1. 攻撃
・プロンプトインジェクション：特殊な入力でAIの出力を乗っ取る手口
　起きること：内部情報の流出／モラルに欠けた回答／第三者の個人情報・機密情報の開示／違法行為の助長
・プロンプトリーク：事前設定（システムプロンプト）が利用者に読まれてしまう → 漏れる前提で作る
・ジェイルブレイク：AIサービスの制約を外させる行為。利用規約違反。断られたら繰り返さない
・目的は「やり方を覚える」ではなく「こういう攻撃があると知って守る」
・リスク低減：入出力フォーマットの指定／NGワードの設定／攻撃を検知する仕組み／ログの収集・分析
　→ 行うのはAIの前後（アプリケーションの側）
・作ったエージェントの共有範囲（誰まで見えるか）を必ず確認する

■2. 間違いと偏り
・ハルシネーション：間違った情報を、正しいかのように自信を持って答える
　原因は第1章の仕組みそのもの（「ありそうだから」選んでいる）。だからゼロにはできない
・対策：ファクトチェック（出典を聞くだけでなく中身を読みに行く）／出典を求める／RAG
・RAG：資料を検索して、プロンプトに足してから聞く仕組み
　手で足すのが In-Contextラーニング、自動で検索して足すのが RAG
・バイアスの原因は3つ：学習データの偏り／聞き方の偏り／時間による偏り（古いデータ）
・AIの答えを「中立な第三者の意見」として扱わない
・同意を求める聞き方をすると、AIは同調しやすい。「前提に誤りがあれば指摘して」と書いておく

■3. 情報の扱い
・入力した内容が学習に使われる可能性がある（扱いはサービス・プラン・設定で異なる。利用規約と社内ルールを確認）
・対策5つ：匿名化（名前やアドレスをXXXXに置き換える）／機密データの除外／質問の一般化／内部ガイドラインの策定／適切なサービスの使用
・個人情報＝法律で第三者提供が禁止されているもの。機密情報＝社内ポリシーで守るもの。根拠が違う
・著作権は2つに分けて考える
　1. AIの出力に著作権が発生するか → 日本では原則発生しないとされる（人が創作的に手を加えた部分は別）
　2. AIの出力が他人の著作権を侵害しないか → 極端に似ている／特徴的な表現のコピー／著作物を入力して似せた場合はリスクが高い
・結論：AIの出力をそのまま社外に出さない。人が確認して手を入れる。個別の案件は法務に確認

■明日から、まず1つだけ
いつも使っているプロンプトに、出力形式を1行足す。

補足：プロンプトでよく使う記号
【補足：プロンプトでよく使う記号】

#（シャープ）　見出しの目印
　例：# 前提ルール　# 出力してほしい形式

-（ハイフン）　条件やステップを1行ずつ並べる
　例：- 専門用語を使わない　- 3行以内で書く

###　指示と対象（材料）を分ける区切り
　例：
　以下の文章を要約してください
　###
　（ここに文章）

"""（ダブルクォーテーション3つ）　「ここからここまでが参照する文章」という境界
　例：
　次の文章を直してください。
　"""
　お疲れ様です。明日の会議ですが…
　"""

［ ］（角カッコ）　役割の指定や、「ここには後で言葉が入る」という目印
　例：[役割: プロの編集者]　[ここに要約したい文章を入れる]

{ }（波カッコ）　差し替え用のキーワード、データのまとまり
　例：{ユーザーの質問}

／（スラッシュ）　選択肢を並べる
　例：賛成／反対／どちらでもない

<タグ></タグ>　内容を箱のように囲んで、どこからどこまでが何かを分ける
　例：<ルール>敬語で答えてください</ルール>

※記号は「ルールだから通じる」のではなく、AIが読んだ文章に多かったから通じやすい。
　使わなくても伝わるが、使うとはっきりする。#の数は1つでも3つでもよい。
